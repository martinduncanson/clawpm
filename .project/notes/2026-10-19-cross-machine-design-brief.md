Date: 2026-10-19. Status: INPUT TO THE PLANNER, not a decision. Operator decision (Martin, 2026-10-19): he wants a robust, real multi-machine, multiple-writer setup. The "single-allocator rule" option is rejected as the end state. ## Constraints to carry into the spec
1. Shared substrate. The `fork` remote (github.com/martinduncanson/clawpm style remote per repo) is the only thing every machine already shares. A remote ledger means reopening AgentICQ, mothballed in `~/.claude/decisions.md` (2026-09-02 and provisionally 2026-10-04). If the design uses it, the ADR must say it reverses that decision.
2. Scope is ALL per-machine state, not just ids. List every piece keyed on `portfolio_root` or a local `file_lock`: `id_reservations.jsonl`; the prefix-allocation lock and the research lock; dispatch locks, lease holder tokens and leases; the session registry and inbox; the global portfolio registry; the `.project/` task-file write path. Memory `cross_project_isolation.md` lists 9 same-id/different-project corruption sites. Fixing only ids leaves leases two machines can both hold.
3. CLAWP-061's hard rule: readable files stay the source of truth; refs (if used) are a derived index.
4. Prefer compat over hard-fail (memory `feedback_prefer_compat_over_hard_fail_clawpm.md`): existing single-machine projects keep working with zero config; multi-machine is opt-in per project.
5. Windows + Linux, CRLF safe. Auto-minted id shape `PREFIX-NNN` (and `PREFIX-NNN-NNN` children) must be the shape used in tests, not hand-picked ids (memory `feedback_test_against_realistic_autogenerated_ids.md`).

## Two questions that decide the mechanism (ask Martin FIRST)
Q1. Must a machine mint task ids while OFFLINE (no route to the remote)?
  - Yes -> reserve a BLOCK of ids per machine ahead of time and mint locally from it (blocks reserved atomically on the remote).
  - No -> reserve each id with an atomic compare-and-swap on the remote at mint time; fail loudly when offline.
Q2. Can two machines work the SAME task at the same time?
  - Yes -> claims/leases must be exclusive across machines (a remote-arbitrated lease with expiry and a fencing token).
  - No -> ids plus a merge discipline for task files is enough; leases stay machine-local.

## Candidate primitive to test (do NOT assert from docs)
Create a git ref atomically on the fork (`refs/clawpm/<project>/ids/<n>` or a counter ref), create-only. VERIFY BY EXPERIMENT against a real bare remote and against GitHub that creating a ref that already exists is rejected and that the loser sees a clear error (memory `feedback_verify_tool_behaviour_by_running_it.md`). Also test: concurrent create from two clones, a force-push attempt, a stale clone, and an offline clone reconnecting.

## Alternatives the spec must weigh (one recommendation, not a survey)
- Git-ref reservation (CLAWP-061 path): no new infra, uses the existing remote; limited to what refs can express (no TTL, so expiry needs a convention).
- Machine-id prefix in the id (e.g. `CLAWP-m2-NNN`): zero coordination, but changes the id shape everywhere (parsers, tests, MCP, docs). Cheap, ugly, breaks the compat constraint unless opt-in.
- Remote ledger service (AgentICQ / a small service): strongest semantics, biggest cost, reverses a mothball decision.
- Single allocator: rejected by the operator as the end state; still valid as an interim documented rule until the build lands.

## Test harness requirement
Two real clones against one bare remote (plus an optional GitHub-backed run behind an env flag), driven concurrently; assertions on: no duplicate ids under N parallel mints from 2 clones; lease exclusivity (if Q2 = yes); behaviour on partition and rejoin; single-machine projects unchanged.
